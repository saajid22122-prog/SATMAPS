## 1. THE PROBLEM

India's Integrated Watershed Management Programme (IWMP) funds check dams, farm ponds, and percolation tanks to restore degraded rural land. NRSC/ISRO's SRISHTI (satellite monitoring) and DRISHTI (geo-tagged ground photos) collect data on this, but a human analyst currently has to manually compare satellite imagery against ground photos, with no systematic check for whether an apparent "success" is really just explained by rainfall. This system automates that specific workflow, adds a rainfall-attribution check the manual process lacks entirely, and routes any uncertainty to the exact right domain specialist instead of a generic reviewer.

This is a demo-ready prototype, not an official government deployment — no formal NRSC/DoLR data-sharing agreement exists yet. State this honestly wherever project scope is discussed.

## 3. DOMAIN-BY-DOMAIN BREAKDOWN — WHERE EACH REAL-WORLD EXPERTISE FITS, HOW IT'S BUILT, WHAT IT CONTRIBUTES

This system is modeled on five real institutional roles from India's actual watershed governance structure (WDT — Watershed Development Team — plus the village Watershed Committee). Each one maps to a specific, buildable piece of the app — not a generic "reviewer."

### 3a. Water Management Expert
**Real-world role:** Designs/assesses water-harvesting structures — capacity, siting, structural soundness.
**What triggers their review:** Layer 3's cross-validation detects a mismatch specifically about water presence (e.g. satellite shows no water signature but the photo/report claims a functioning farm pond).
**What they're shown, and where each piece comes from:**
- The real ground photo (`Photo.file_path`)
- A live/stored Sentinel-2 NDWI reading for that exact coordinate (Google Earth Engine — real, computed, never guessed)
- The structure's build/sanction date (from the source record)
**How it's built:** A dedicated form component (`WaterManagementForm.tsx`) that queries only these fields via a role-scoped API endpoint. Their submitted judgment (functional / silted / breached / etc.) writes to `ExpertReview` and can override the automated status.
**Contribution:** This is the closest thing to ground-truth structural verification the system has — their judgment is treated as more authoritative than the automated classification for water-presence questions specifically.

### 3b. Agriculture Expert
**Real-world role:** Assesses land/crop suitability, cropping patterns.
**What triggers their review:** A detected land-cover transition (e.g. "scrub → agriculture") that needs a plausibility check for that specific location and season.
**What they're shown:** Real baseline LULC (Bhuvan `GetFeatureInfo`) vs. real current LULC (Google Earth Engine Dynamic World, queried as an annual `.mode()` composite — never `.first()`, which returns null in cloudy regions), plus district and date.
**How it's built:** `AgricultureForm.tsx`, same role-scoping pattern.
**Contribution:** Catches cases where a detected "vegetation increase" doesn't actually make agronomic sense for that specific place/time — a check the current manual government process does not perform at all.

### 3c. Soil Science Expert
**Real-world role:** Assesses soil type, erosion risk.
**What triggers their review:** Structures where soil condition is relevant to judging siting/erosion (e.g. gully plugs, contour trenches, or any Disagreement case where soil plausibility might explain it).
**What they're shown:** The real ground photo plus the real soil texture class for that coordinate (OpenLandMap via Google Earth Engine — ISRIC SoilGrids is confirmed unreliable/paused, do not use it).
**How it's built:** `SoilScienceForm.tsx`.
**Contribution:** Adds a domain-grounded plausibility check most automated systems skip entirely.

### 3d. Social Mobilization Expert
**Real-world role:** Community organizing, institutional/Watershed Committee formation.
**What triggers their review:** Governance/community-context questions — this is the role furthest from automatable data.
**What they're shown:** Project ID, district, real village/locality (reverse-geocoded via Nominatim) — and nothing else auto-populated.
**Critical rule:** Never auto-generate a Watershed Committee name or any community-institution detail — this was investigated and confirmed there is no real, reliable naming convention to derive one from (per MoRD's own Common Guidelines). Their form is a free-text field anchored only to real location/project data.
**Contribution:** Captures the one category of information (community/governance reality) that satellite and photo data genuinely cannot answer.

### 3e. Watershed Committee Member (a real local villager, not a government employee)
**Real-world role:** Direct, lived, local knowledge of whether a structure is actually there and working.
**What triggers their review:** A simple functional-status check, especially for `No Evidence` cases.
**What they're shown:** Structure name, village, a location pin — deliberately minimal, since their value comes from personal knowledge, not system-supplied data.
**How it's built:** `CommitteeForm.tsx`, simplified UI (Yes / No / Needs Repair), designed to be usable by someone without technical background.
**Contribution:** This is the system's one genuinely independent verification signal — a human physically near the structure, separate from satellite, photo, and rainfall data entirely.

### The routing logic that ties all five together
Layer 3 sets a `disagreement_type` field on the `CrossValidation` row at the moment cross-validation runs (not computed live when a form opens). Explicit, documented rules map each mismatch pattern to exactly one role — e.g. `satellite_verdict == 'water_detected' AND photo_classification NOT IN (water-related types)` → routes to Water Management. **These rules must be written out explicitly in code comments and be inspectable — this routing logic is the system's core novelty claim, not a black box.**

## 4. RESTREND — FULL, REAL IMPLEMENTATION (not a simplified stand-in)

**What it is:** Residual Trend Analysis — a real, peer-reviewed remote-sensing method for separating rainfall-driven vegetation change from other causes.

**How to actually build it, step by step, using only real data:**
1. Pull the real historical monthly time series for each asset's coordinate: observed NDVI (Google Earth Engine, Sentinel-2/Landsat) and rainfall (IMD via `imdlib`, with Open-Meteo as a confirmed real fallback — never CHIRPS, which was never verified in this project)
2. Run a **real Ordinary Least Squares (OLS) regression**: `NDVI_expected = α · rainfall + β`, fit on the real historical series
3. Compute the real residual per time point: `residual = NDVI_observed − NDVI_expected`
4. Fit a trend line to the residuals over time. If the residual trend is positive with real statistical significance (e.g. p < 0.1, using the actual computed p-value, never assumed), the observed greening is genuinely decoupled from rainfall — a real signal the intervention itself caused the change, not the weather
5. **This is what determines the Rainfall-Confounded vs. Confirmed status** in Layer 3 — not a simple above/below-average threshold
6. Pre-compute this entire calculation once per asset at ingestion time, cache the result (`RainfallTimeseries` table). **Never run this regression live on a user's map click** — a live Earth Engine query for a 10-year monthly series takes 8-15 seconds, which is a broken user experience for something that should feel instant

**Where it's shown:** `RestrendChart.tsx` — a real dual-axis chart (Recharts) plotting observed NDVI, modeled NDVI, and rainfall bars, with the real regression line and real p-value labeled directly on the chart. Never show a chart without the real statistics driving it visible somewhere nearby.

## 5. THE FULL SYSTEM FLOW

**Stage 1 — Field Inspector:** Visits a structure, opens the app, taps "New Inspection," takes a photo. Phone GPS attaches automatically. This is the primary, real-time data path.

**Stage 2 — Storage:** Photo → cloud file storage. A database record (coordinates, timestamp, file pointer) is written immediately.

**Stage 3 — Automatic Backend Triage** (seconds, no human):
1. CLIP classifies the photo
2. Google Earth Engine pulls real before/after satellite imagery
3. IMD/`imdlib` pulls real rainfall; RESTREND regression runs (Section 4)
4. OpenLandMap (soil) + Copernicus DEM (elevation/slope) add real terrain context
5. Cross-validation logic combines all of this into: **Confirmed / Rainfall-Confounded / Disagreement / No Evidence**, with a `disagreement_type` set if flagged

**Stage 4 — Result propagation:** Written to DB → live map updates immediately → flagged cases join the Review Queue.

**Stage 5 — Targeted expert routing:** Per Section 3's routing logic — exactly one matching specialist reviews it.

**Stage 6 — Report export:** Pulls everything already in the database into a PDF styled per Section 11.

## 10. DEPLOYMENT STABILITY — DO NOT LET THIS CRASH

**CLIP memory (critical):** torch + transformers + CLIP weights are 1-2GB+; free-tier hosts typically cap RAM at 512MB-1GB.
- Run CLIP embedding extraction as a **one-time offline batch script** → `clip_embeddings.npz`
- The deployed API loads only the lightweight scikit-learn linear probe + precomputed embeddings
- For live field-upload classification, run single-image CLIP inference through a separate lightweight service/function if the main API's RAM budget can't absorb it — confirm the real hosting tier's RAM limit before deploying, don't assume

**Database framing:** SQLite is dev-only. Production is PostgreSQL + PostGIS via `DATABASE_URL` — this must actually be tested working, not just claimed as a talking point.
